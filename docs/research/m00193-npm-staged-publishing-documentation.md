**Repository:** `/home/lovedolove/projects/Veyra`
**Workflow:** `.github/workflows/publish-npm.yml`
**Reference release:** `v0.2.0` (`dd22b6317109626d406eead507842ae45f6b08f5`)
**Verdict:** **DOCUMENTATION_COMPLETE**

Every command, output line, and timestamp in this document was executed or read from the v0.2.0 release artifacts during this round. Nothing here is inferred from general npm knowledge; where something could not be verified it is listed in §9 as undocumented.

## 1. The problem this document solves

A Veyra release does **not** become installable when the publish workflow turns green. The workflow runs `npm stage publish`, which uploads the tarball and the provenance statement but deliberately **defers the proof-of-presence (2FA) check to a later, human step**. Until a maintainer approves the staged package, `https://registry.npmjs.org/@lovedolove/veyra/<version>` returns **HTTP 404**.

For v0.2.0 that window was real and observable:

| Moment (UTC) | State |
| --- | --- |
| `14:49:09` | workflow reports `+ @lovedolove/veyra@0.2.0 (staged with id d9d47d55-…)` |
| `14:49:14` | GitHub Release `v0.2.0` created — **while npm still 404s** |
| `14:49:17` | publish run finishes `success` |
| `14:53:54` | registry `time["0.2.0"]` — package is live |

Four minutes and forty-five seconds in which a green workflow, a published GitHub Release, and a 404 on npm were all simultaneously true. That is not a failure — it is the designed approval gate — but without this document it looks exactly like a broken release.

The same shape appeared for `v0.1.75`: staged `12:04:34`, live `12:07:31` (≈3 min).

## 3. The three states a release passes through

These are genuinely different states with different observable consequences. Conflating them is the source of most release confusion.

### State 1 — Staged publication

The tarball, its integrity hash, and the SLSA provenance statement exist in npm's staging area. Nothing is installable.

Verbatim from the v0.2.0 run log (step 8):

```
npm notice Tarball Details
npm notice name: @lovedolove/veyra
npm notice version: 0.2.0
npm notice filename: lovedolove-veyra-0.2.0.tgz
npm notice package size: 262.0 kB
npm notice unpacked size: 855.6 kB
npm notice shasum: 64034109c7adc5664c1931bf247d3c52e9758bb5
npm notice integrity: sha512-8NF/z32lot8u3[…]OFiXAEWfwB9ow==
npm notice total files: 52
npm notice Staging to https://registry.npmjs.org with tag latest and public access
npm notice stage Signed provenance statement with source and build information from GitHub Actions
npm notice stage Provenance statement published to transparency log: https://search.sigstore.dev/?logIndex=3787960777
+ @lovedolove/veyra@0.2.0 (staged with id d9d47d55-8f27-40cf-90ab-75d402b5d88b)
npm notice stage package @lovedolove/veyra@0.2.0 has been staged with tag latest
```

Observable state: `GET .../veyra/0.2.0` → **404**; `dist-tags.latest` → still the previous version (`0.1.75` for v0.2.0); `npm stage list` (authenticated) → the version appears with its stage id.

### State 2 — Pending manual approval

Identical to State 1 from the outside; the difference is intent. The package is staged and waiting for a maintainer with publish rights on `@lovedolove` to approve it. This can last as long as the maintainer takes — for v0.2.0 it was under five minutes, but nothing in the workflow bounds it.

During this window the GitHub Release already exists, because step 9 runs immediately after staging. A reader who sees the Release and then gets a 404 from npm is seeing State 2, not a broken release.

### State 3 — Final npm Registry publication

The version is immutable and installable.

Observable state (all verified live at the time of writing):

| Check | Command | Value |
| --- | --- | --- |
| version resolves | `npm view @lovedolove/veyra@0.2.0 version` | `0.2.0` |
| `latest` points at it | `npm view @lovedolove/veyra dist-tags.latest` | `0.2.0` |
| registry returns 200 | `curl -o /dev/null -w '%{http_code}' https://registry.npmjs.org/@lovedolove/veyra/0.2.0` | `200` |
| publish timestamp | (see §6) | `2026-11-10T14:53:54.277Z` |

## 4. The manual approval / 2FA step

This is the step that moves a package from State 2 to State 3. It is performed by **a human with publish rights**, using an authenticated npm session.

**What the CLI offers** (`npm stage --help`, npm 12.2.2, verbatim):

| Subcommand | Description |
| --- | --- |
| `publish` | stage a package ("deferring proof-of-presence (2FA) to a later point in time") |
| `list` | "List all staged package versions" |
| `view <stage-id>` | "View details of a specific staged package" (aliases `info`, `show`, `v`) |
| `approve <stage-id>` | **"Approve a staged package, publishing it to the npm registry"** |
| `reject <stage-id>` | "Reject a staged package, removing it from the registry" |
| `download <stage-id>` | "Download the tarball of a staged package for inspection" |

`approve` and `reject` accept `[--otp <otp>] [--registry <registry>]`, where `--otp` is documented as "This is a one-time password from a two-factor authenticator."

**Prerequisite — an authenticated session.** Staged-package commands refuse to run without valid credentials. Running them unauthenticated produces exactly:

```
npm error code E401
npm error Unable to authenticate, your authentication token seems to be invalid.
npm error To correct this please try logging in again with:
npm error   npm login
```

To use `npm stage list` / `view` / `approve`, a maintainer must first `npm login` as an account with publish rights on `@lovedolove`. The approval itself is the account's 2FA proof-of-presence.

**What this repository actually does.** There is no wrapper script and no recorded command — the approval is a manual operator action. The evidence that it happened, and that it happened as a human action, is registry-side in `_npmUser`:

```json
{
  "name": "GitHub Actions",
  "email": "npm-oidc-no-reply@github.com",
  "trustedPublisher": { "id": "github", "oidcConfigId": "***" },
  "approver": { "name": "lovedolove", "email": "v0130p5100cuboss@gmail.com" }
}
```

`name` is the CI identity that *staged* the package (OIDC), and `approver` is the human account that *approved* it. The presence of a populated `approver` is proof of the manual gate. On v0.1.75 the same structure appears.

> **Do not** attempt to script the approval with a token. The registry itself warns at this point: *"npm tokens that bypass 2FA are being restricted for account changes and direct publishing."* A token that bypasses 2FA is precisely what staged publishing exists to avoid.

## 5. Why a staged package returns HTTP 404

The 404 is correct and expected, not an error to debug.

1. **The version is not published yet.** `npm stage publish` writes to a staging area, not to the version index. `GET /@lovedolove/veyra/<version>` resolves against the published version index, which does not contain the staged version, so the registry answers as it would for any version that does not exist: `{"error":"version not found: 0.2.0"}`, **HTTP 404**.
2. **`dist-tags` cannot move.** Because the version is not published, `latest` still points at the previous version. For v0.2.0 it read `{"latest":"0.1.75"}` during the window.
3. **404 is exactly what the workflow expects.** `Validate version` treats 404 as "version is free, proceed" and 200 as "version already exists, stop". Both facts come from one rule: 404 means *absent*, 200 means *present*. Verified live — `0.2.0` → `200`, `9.9.9` → `404`.

The practical consequence: **404 during the approval window is normal; 404 after the approver reports success is a real problem** (see §7).

## 6. Verifying final publication

Run these after the maintainer approves. All commands below were executed this round against the live `0.2.0`.

### 6.1 Version resolves

```bash
npm view @lovedolove/veyra@0.2.0 version
# 0.2.0
```

An unstaged/absent version returns a non-zero exit and `E404`.

### 6.2 `latest` dist-tag points at it

```bash
npm view @lovedolove/veyra dist-tags.latest
# 0.2.0
```

Flat field access works; `--json` also works and returns `{ "latest": "0.2.0" }`. This is the check that distinguishes "published" from "published but nobody gets it by default" — a version can exist while `latest` still points elsewhere.

### 6.3 Registry availability

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://registry.npmjs.org/@lovedolove/veyra/0.2.0
# 200
```

### 6.4 Publish timestamp

A dotted version number cannot be used as an `npm view` field path — `npm view @lovedolove/veyra time.0.2.0` prints **nothing** (it is silently empty, not an error). Use one of:

```bash
# npm view returns an array-wrapped object here
npm view @lovedolove/veyra time --json \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const j=JSON.parse(s);const o=Array.isArray(j)?j[0]:j;console.log(o["0.2.0"])})'
# 2026-11-10T14:53:54.277Z

# or read the packument directly
curl -s https://registry.npmjs.org/@lovedolove/veyra \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>console.log(JSON.parse(s).time["0.2.0"]))'
```

The `time` entry is the moment the human approval took effect, not the moment CI staged the package. The gap between them is the approval window.

### 6.5 Signature and provenance

```bash
# are attestations attached?
npm view @lovedolove/veyra@0.2.0 dist.attestations
curl -s -o /dev/null -w '%{http_code}\n' \
  "https://registry.npmjs.org/-/npm/v1/attestations/@lovedolove%2fveyra@0.2.0"
# 200
```

In a consumer project that has installed the package:

```bash
npm audit signatures
# 2 packages have verified registry signatures
# 2 packages have verified attestations
```

Machine-readable:

```bash
npm audit signatures --json
# { "invalid": [], "missing": [] }
```

`invalid: []` and `missing: []` are the pass condition — an empty `invalid` means no signature failed, an empty `missing` means every installed package carried one.

**Tarball identity** — the value that ties the published bytes to the tested commit:

```bash
npm view @lovedolove/veyra@0.2.0 dist.shasum dist.integrity
# 64034109c7adc5664c1931bf247d3c52e9758bb5
# sha512-8NF/z32lot8u3JeT7kE2CAmdWm0IKnuuPbn7lVUjhLa79zekHZkfuv2pnEbfDjXrzc1Vnq7BeOFiXAEWfwB9ow==
```

That shasum must equal the `shasum:` printed by the workflow's stage step, and — critically — must equal a **`git archive` repack**, not a working-copy `npm pack`. The working copy carries CRLF endings that Git normalises on commit, so a working-copy pack yields a different hash (for `0.2.0`: `8daca27d…` vs the correct `64034109…`). See §8.

**Provenance binding.** The SLSA statement at the attestations endpoint carries:

```
predicateType: https://slsa.dev/provenance/v1
buildType:     https://slsa-framework.github.io/github-actions-buildtypes/workflow/v1
workflow:      .github/workflows/publish-npm.yml
ref:           refs/tags/v0.2.0
repository:    https://github.com/LoveDoLove/Veyra
commit:        dd22b6317109626d406eead507842ae45f6b08f5
```

Confirm `commit` equals the tag's commit (§6.6). If they differ, the published artifact was not built from the tagged source.

### 6.6 GitHub Release and tag consistency

```bash
git rev-parse v0.2.0            # 0b3e1410…  → tag OBJECT
git rev-list -n1 v0.2.0         # dd22b63…   → COMMIT the tag points at
git ls-remote --tags origin v0.2.0   # must equal the local tag object
gh release view v0.2.0 --json tagName,targetCommitish,isDraft,createdAt,url
```

For v0.2.0:

```json
{"createdAt":"2026-11-10T14:48:24Z","isDraft":false,"tagName":"v0.2.0","targetCommitish":"main","url":"https://github.com/LoveDoLove/Veyra/releases/tag/v0.2.0"}
```

Local tag object `0b3e1410…` == remote tag object `0b3e1410…`, and the tag resolves to `dd22b63…` — the same commit named in the SLSA provenance. `isDraft: false` confirms the Release is public.

**Order to check, and why:** tag → commit → provenance commit → published shasum. A break anywhere in that chain means the artifact on npm is not the artifact the repository describes, regardless of how green the run looked.

## 7. Handling pending, failed, or abandoned staged publications

The governing rule: **staging is not idempotent, and re-running a publish is not a retry.** Approaching a non-`live` state by pushing again is how you get a half-released version.

### 7.1 The version is staged, CI succeeded, npm 404s

**This is the normal approval window.** Do nothing except approve.

1. Wait — confirm the state is genuinely fresh by comparing the run's stage timestamp with `time["<version>"]` (§6.4). If the gap is minutes, you are mid-window.
2. To inspect what is pending, an authorised maintainer runs `npm login`, then `npm stage list`, then `npm stage view <stage-id>` to confirm the tarball and provenance look right before approving.
3. Approve: `npm stage approve <stage-id>` (2FA prompt). Then re-run §6.

**Do not** re-push the tag or re-dispatch the workflow to "kick" it. The tag-triggered run already succeeded; the hold-up is the approval, and a second run cannot approve anything.

### 7.2 The publish workflow itself fails

A failure **before** `Stage publish to npm` means nothing reached npm — those steps are ordered ahead of it and the job stops at the first unfixed failure:

| Failing step | Meaning | Action |
| --- | --- | --- |
| `npm test` | the tree is not releasable | fix, do not publish |
| `Runtime dependency check` | an undeclared bare import | fix `package.json`, do not publish |
| `Validate version` | tag/version mismatch, or version already on npm | see 7.3 / 7.4 |

A failure **inside or after** `Stage publish to npm` (for example the provenance upload, or the Release step) is a different situation and must not be assumed to have left nothing behind — the tarball may already be staged. Confirm before acting:

```bash
npm login
npm stage list        # is this version present? note its stage id
```

If it is listed, the release is in State 2 and needs §7.4 handling, not a re-run. If it is absent, staging genuinely did not happen and the error from the failing step is the thing to fix. Never retry blindly: `npm stage publish` is not idempotent for a version that is already staged.

### 7.3 `Validate version` reports the version already exists (HTTP 200)

The version is **taken and immutable**. npm does not permit re-publishing a version.

Correct response: pick a new version, update `package.json` + `CHANGELOG.md`, tag that new version. Never attempt to force or overwrite the existing one.

### 7.4 A staged package must be abandoned

If the staged tarball is wrong and npm already holds it, remove the staged entry before doing anything else:

```bash
npm stage reject <stage-id>      # "Reject a staged package, removing it from the registry"
```

Verified: `reject` is the CLI's documented removal path for a staged entry, and it accepts `[--otp <otp>]` like `approve`. Not verified this round: whether npm would also *refuse* a second `npm stage publish` for a version that already has an outstanding stage, or whether it would silently create a second staged entry. Treat re-staging without a reject as unsafe rather than assuming it fails cleanly — inspect with `npm stage list` after any reject and before re-staging.

**Before rejecting**, be certain: if the version was already approved and is live, `reject` is no longer the tool (`npm unpublish` semantics apply, and this repository's policy is that published versions are immutable — release forward, never rewrite).

### 7.5 A release is live on npm but the GitHub Release is missing or wrong

Harmless to the package; fix the Release directly. The npm artifact and its provenance do not depend on the Release. Do not re-run the publish workflow to regenerate a Release for an already-live version — `Validate version` will correctly refuse it.

### 7.6 A release is live on npm with no Git tag

Treat as a process defect. The tag is what the provenance `ref` names; without it the published artifact cannot be traced back. Do not delete the package; add and push the tag for the commit that was actually built, verify against the provenance `commit` field, and record the miss.

### 7.7 Checklist before ever touching the registry

- The version exists on npm? → **stop**, choose a new version.
- A stage is outstanding for this version? → `npm stage list` before anything else.
- About to run `npm stage publish` from a working copy? → **stop**; only CI stages (`docs/agent-guides/release-and-packaging.md`: "Do not push tags, dispatch the workflow, or run a publish from a working copy unless the user explicitly asks for a release.").

## 8. Two operational traps learned from v0.2.0

### 8.1 A working-copy pack never reproduces the published shasum

| Source | shasum | size |
| --- | --- | --- |
| working copy `npm pack` | `8daca27df1a7ccbf589751358b663c6529d74a95` | 262.6 kB |
| `git archive HEAD \| tar -x` then `npm pack` | `64034109c7adc5664c1931bf247d3c52e9758bb5` | 262.0 kB |
| CI published (registry `dist.shasum`) | `64034109c7adc5664c1931bf247d3c52e9758bb5` | 262.0 kB |

Cause: the working copy holds CRLF endings that Git normalises to LF on commit — `src/text.mjs` 97, `src/evolve.mjs` 584, `src/diff.mjs` 168, `skills/legacy-onboarding/SKILL.md` 269 occurrences; the committed blobs contain zero CRLF. Always compare against a `git archive` pack.

### 8.2 `--dry-run` is safe, and this is verified

`npm stage publish --dry-run` builds the tarball and prints every notice, but marks every registry-facing line `(dry-run)` and never contacts the registry with a payload:

```
npm warn stage This command requires you to be logged in to http://127.0.0.1:1/ (dry-run)
npm notice Staging to http://127.0.0.1:1/ with tag latest and public access (dry-run)
+ @lovedolove/veyra@0.2.0 (staged)
npm notice stage package @lovedolove/veyra@0.2.0 has been staged with tag latest
[exit: 0]
```

Verified by pointing `--registry` at an unreachable address (`http://127.0.0.1:1/`): the command exited 0 and left the working tree clean, proving no network write is required. Note the misleading final line — it says "has been staged" even under `--dry-run`; the `(dry-run)` markers are the only reliable signal.

## 9. Still undocumented / unverified

Stated plainly rather than papered over:

- **No recorded approval command.** This repository has never documented which operator ran `npm stage approve`, or when. The approval is evidenced only by the registry's `_npmUser.approver` field. Adding the exact command to a release log would close this.
- **No documented approval URL.** npm's web UI path for approving staged packages was not verified this round, so none is given here. The CLI is the verified path.
- **Approval latency is unbounded** by the workflow. v0.2.0 took ≈4m45s and v0.1.75 ≈3min, but those are observations, not a guarantee, and there is no automation or alerting if an approval is never made.
- **`npm stage list` could not be exercised end-to-end** locally: the host's `.npmrc` token is invalid (`E401`), so the authenticated `list`/`view`/`approve` flow is documented from CLI help text plus the registry's `approver` evidence, not from a successful local approval run.
- **`npm help stage` is unavailable on this host** (`EACCES` on the man page, `col: command not found`), so `--help` output is the authoritative source used throughout.
- **A node-deprecation warning rides along**: `Node.js 20 is deprecated. The following actions target Node.js 20 but are being forced to run on Node.js 24: actions/checkout@v4, actions/setup-node@v4, softprops/action-gh-release@v2.` Non-blocking, but it will need action-version bumps eventually.

## 10. Release checklist for maintainers

```text
Before tagging
  1. package.json version == CHANGELOG.md heading == intended tag       (X.Y.Z only; no prerelease)
  2. npm test green                                                     (1110/1110/0 at v0.2.0)
  3. node scripts/runtime-deps-check.mjs green
  4. npm run pack:check shows exactly the intended files                (52 files at v0.2.0)
  5. git archive HEAD | tar -x → npm pack → note the shasum             (this is the expected shasum)
  6. Version absent from the registry
       curl -s -o /dev/null -w '%{http_code}' https://registry.npmjs.org/@lovedolove/veyra/<X.Y.Z>
       expect 404
  7. README / guides updated for any behaviour change; no unrelated diff; no secrets

Release
  8. Commit, then create an ANNOTATED tag:  git tag -a v<X.Y.Z> -m "…"
  9. Push the branch, then the tag:         git push origin main && git push origin v<X.Y.Z>
 10. Watch the Actions run: the `Stage publish to npm` step must print
       "+ @lovedolove/veyra@<X.Y.Z> (staged with id <uuid>)"
       and "has been staged with tag latest"
       Record the stage id.

Approval gate  (STATE 2 — npm will 404 here; this is expected)
 11. Confirm the hold-up is approval, not failure: the run should be `success`,
     and the registry still 404 while the Release already exists.
 12. npm login   (account with publish rights on @lovedolove)
 13. npm stage list                        → confirm the version + stage id
 14. npm stage view <stage-id>             → confirm tarball size/files/provenance
 15. npm stage approve <stage-id>          → 2FA prompt; this is the publish

After approval  (STATE 3)
 16. npm view @lovedolove/veyra@<X.Y.Z> version           → <X.Y.Z>
 17. npm view @lovedolove/veyra dist-tags.latest          → <X.Y.Z>
 18. registry HTTP status                                  → 200
 19. dist.shasum == the shasum recorded in step 5
 20. npm audit signatures (in a consumer install)          → invalid: [], missing: []
 21. attestation commit == git rev-list -n1 v<X.Y.Z>
 22. gh release view v<X.Y.Z>                              → isDraft false, tagName matches
 23. local tag object == remote tag object

If anything fails
 24. Never re-push the tag to "retry" a staged or live version.
     Staged-but-wrong  → npm stage reject <stage-id>, then re-stage.
     Already live      → release forward with a new version; never rewrite.
```
